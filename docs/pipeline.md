# Pipeline: from `game/` to `src/`

`osu!.exe` 1.3.3.8 is an x86 .NET Framework 4 assembly protected by Eazfuscator.NET: 2907
types and 21398 methods, 92 % of the type names and 86 % of the method names encrypted, every
string encrypted behind one decryptor (9444 call sites), 27 methods virtualized, the game's
resources moved into an encrypted embedded assembly. Generic tools stop at the strings: the
decryptor inspects its caller and answers a decoy.

These scripts undo that protection in a local copy of a binary you already have, to read its
code. Using them to infringe the rights in the software is punishable as copyright
infringement: see [`LEGAL.md`](../LEGAL.md).

Everything under `work/` and `src/` is regenerated by one command. Neither is in git:
`src/` is the game's code, and [`src.sha256`](../src.sha256) is the fingerprint that tells
whether a machine generated the same source as the reference one.

```powershell
.\scripts\pipeline.ps1               # everything
.\scripts\pipeline.ps1 -From names   # after a change of docs/names.tsv
.\scripts\pipeline.ps1 -From decomp  # after a change of the decompiler or of its tables
.\work\app\release\ochu-cli.exe src-manifest --verify   # src/ is the reference source
```

The order of the stages, the copy and the `src` stage are in `app/src` (Rust:
`pipeline.rs`, `srcstep.rs`), and `pipeline.ps1` only runs that program. The stages that
read or write .NET metadata are the PowerShell and C# of `scripts/`, which it calls: they
load `dnlib`, run the game's own string decryptor in a 32-bit .NET Framework, or are the
decompiler itself. After a change that is meant to change `src/`, and once the checks of
[`matching.md`](matching.md) pass, `ochu-cli.exe src-manifest` writes the new fingerprint.

| Stage | Output | What it does |
|---|---|---|
| `copy` | `work/triage/in/` | copies the assemblies out of `game/`, which is only ever read |
| `strings` | `work/deobf/osu!.strings.exe`, `work/resources/raw/` | `decrypt-strings.ps1` replaces each call of the decryptor by its string; `extract-resources.ps1` reads the game's 28 resources out of the embedded assembly |
| `clean` | `work/deobf/osu!.clean.exe` | `undo-obfuscator.ps1 -Devirtualize` writes the virtualized methods back as CIL and undoes the obfuscator's edits of method bodies. **This file is the IL reference** |
| `rename` | `work/deobf/osu!.renamed.exe`, `work/decomp/symbols.tsv` | de4dot gives valid generic names (`Class123`, `method_4`) to the encrypted ones; `dump-symbols.ps1` writes the token index |
| `names` | `work/deobf/osu!.named.exe`, `work/resources/build/` | `apply-names.ps1` applies [`names.tsv`](names.tsv), puts back the method bodies of the reference (de4dot rewrites about 2500 of them), recreates properties, events and compiler-generated names; `export-resources.ps1` prepares the resources for the build |
| `decomp` | `work/decomp/raw/` | `scripts/decompiler` writes the C# (C# 7.3), `make-il-unit.ps1` the methods kept as IL |
| `src` | `src/` | copy of the text sources of `work/decomp/raw` into an emptied `src/`, removal of the nullable attributes of Newtonsoft.Json, then [`fixups.tsv`](fixups.tsv) |

Metadata tokens (`0x02...` types, `0x06...` methods, `0x04...` fields) are the same in the
original and in every output: they are the stable references of the tables in `docs/`. The
methods the `clean` stage recreates get new tokens after the last original one
(`0x06005396`); those are not stable and are never cited.

Two stages execute code of the game, in a 32-bit PowerShell that loads a copy of the
assembly without running its entry point: the string decryptor (relayed through a method added
to `<Module>`, the one caller it accepts) and the resolver of the embedded assembly. Nothing
else of the game runs, and nothing touches the network.

## The `clean` stage

The obfuscator does more than rename and encrypt: it edits code. What it added has no C#
source, so no recompilation gives it back. `undo-obfuscator.ps1` undoes it in the reference
(163 methods), and refuses to write when a site does not have the exact expected shape:

- small methods inlined at every call site and deleted (the mod checks of `ModManager`, the
  MD5 helpers of `CryptoHelper`, a few methods of `Player`, `BanchoClient` and `Score`) are
  recreated and called again;
- integer constants mutated into runs of `not` / `neg`, a method looked up by token instead of
  by name: written back as the compiler writes them;
- the game's resources go back into the module, in place of the encrypted assembly;
- the 27 virtualized methods are written back as CIL.

**Devirtualization.** The virtual machine is obfuscator code like any other: it is
decompiled, it matches, and its reader and handlers can be read in `src/Obfuscator`.
`scripts/lib/Devirt*.cs` do the same reading: `devirt/dump-stream.ps1` extracts the virtual
code, [`vm-opcodes.tsv`](vm-opcodes.tsv) maps each of the 204 handlers to the CIL instruction
it executes, and `devirt/devirtualize.ps1` emits the bodies. Short and long forms have
distinct virtual opcodes, so the original IL comes back instruction for instruction. One
method keeps part of its code encrypted with keys that are not in the binary: they are in
[`vm-block-keys.tsv`](vm-block-keys.tsv), written by `devirt/find-block-keys.ps1`, never by
hand. `devirt/read-vm.ps1` prints what the stream holds.

## The decompiler

`scripts/decompiler` is a small program on the ILSpy engine. With no option it writes what
`ilspycmd -p --nested-directories` writes. It exists because the engine chooses the shape of
the code for readability, while the original IL says which shape the source had: each
`Restore*.cs` transform reads the raw body of the method to decide (early `return` or nested
`if`, direction of a conditional, where a captured variable is declared, a `callvirt` on a
non-virtual method, the order of the blocks...). A rule that does not read the IL ends up
losing methods elsewhere.

Three tables tune it:

| Table | Content | Written by |
|---|---|---|
| [`decompiler-hints.tsv`](decompiler-hints.tsv) | decompiler options for single methods | `scripts/tune-decompiler.ps1`, never by hand |
| [`fixups.tsv`](fixups.tsv) | one-line replacements applied to `src/` for what the decompiler cannot get right; the note gives the IL that justifies each | by hand |
| [`units.tsv`](units.tsv) | the types and methods that belong to another compilation unit ([`matching.md`](matching.md)) | by hand |

In `fixups.tsv` the searched text must occur exactly once in its file, or the pipeline stops.
`re:` makes it a regular expression (one match expected), `re*:` replaces every match.

## Naming

Names live in [`names.tsv`](names.tsv), one line per symbol: `token<TAB>name<TAB>evidence`.
`src/` is regenerated, so a name written there is lost.

1. Find the symbol in `src/` or `work/decomp/raw` and its token in `work/decomp/symbols.tsv`
   (that index uses de4dot's generic names, which do not change for a given input).
2. Add the line, then `.\scripts\apply-names.ps1 -CheckOnly` and `.\scripts\pipeline.ps1 -From names`.
3. Build and run the checks of [`matching.md`](matching.md): a name must not change the rate.

Rules:

- Give the evidence: a string, an API call, the resemblance with a public library. Enough for
  someone else to dispute the name. End the note of an uncertain name with `?`.
- Types take their full name with namespace, nested types and members a simple name. Reuse
  the namespaces that survived in the binary (`osu.GameModes.Edit`, `osu_common.Helpers`...)
  instead of inventing some. The obfuscator's own code goes under `Obfuscator`.
- C# conventions: `PascalCase` for types, methods and properties, `camelCase` for fields.
- The obfuscator removed the property and event tables. Name the accessors `get_X` / `set_X`,
  `add_X` / `remove_X`: `apply-names.ps1` then recreates the property or the event.
- Name only the root declaration of a virtual method: its whole group follows. Naming a type
  also renames the fields and parameters whose generic name came from it.
- A property de4dot restored (token `0x17...` in `symbols.tsv`) takes its name directly; an
  explicit interface implementation follows the member it implements.
- Not supported yet: parameters, local variables.
- A name can change what the decompiler writes: accessors named `get_X` / `set_X` become a
  property, and the code that used them is then printed as a compound assignment or an
  object initializer where the IL has neither. `fixups.tsv` holds the few cases; the local
  names of a method also depend on the members around it, so a fixup should not spell them.
- Some names stay generic on purpose: those a fixup of `fixups.tsv` spells in its pattern,
  the members of enums the obfuscator emptied, and what nothing in the code reads.
- A file at the root of `src/` is a type with no namespace. What is left there is the
  compiler's anonymous type (declared outside any namespace) and the types the obfuscator
  emptied (no member, nothing refers to them): nothing in the binary says where they belong.
  A form de4dot named from `InitializeComponent` has no namespace either: give it one, its
  `.resources` follows the type.

`scripts/rank-types.ps1` lists the types that still have a generic name by how often the rest
of the code uses them, with their strings.

## Known limits

- `work/deobf/*.exe` are not made to be run.
- Properties and events are recreated from accessor names: nothing says the original had them.
- A lambda that captures only `this` and a local function without capture are ordinary
  methods in IL: they are decompiled as methods.
- `Score` keeps eleven 256-byte data fields nothing reads any more: the encrypted image of the
  constants of a `switch`, left by the obfuscator.
